Chapter 0

How to use this textbook

Before we start climbing, a short chapter about the staircase itself — what it's made of, where it ends, and how to walk up it without falling off.

What this book is

This is a book about building AI agents, written for someone who has never built one. It starts before agents — before language models, even — and works upward one step at a time until you can design, build, debug, and improve agent systems yourself.

It makes you one promise, and the whole structure depends on it: you will never meet a word before you have met the problem that word solves. Terminology arrives as a solution, never as an assignment. When you read "orchestration" in Chapter 31, it will be because you have already spent two chapters wishing you had a name for something, and orchestration turns out to be that name.

This means the book will occasionally seem to move slowly. Chapter 1 is about what a computer program is — something you already know. Read it anyway. It is not there to teach you what a program is; it is there to name a property of programs that you have always taken for granted, so that when that property breaks in Chapter 8, you feel the break instead of reading past it.

Where we are going

The destination is a hackathon problem. Here it is in its official words, which are currently intimidating and will not be by Chapter 73:

The track statement

"Build a system that can design, test, and improve specialized agents for tasks it has never seen before. Given only a goal, available tools, and a way to evaluate success, your system should generate an agent architecture, run the agent, analyze where it fails, and iteratively improve its prompts, tools, memory, or orchestration strategy."

Now here is the same thing with every intimidating word removed:

The same thing, in plain English

You will build a program that you hand three things to: a description of a job, a box of tools, and a way of checking whether the job got done properly. Your program then writes its own helper to do that job, tries it out, notices what went wrong, fixes the specific thing that went wrong, and tries again — getting better each round.

That is the entire competition. Every frightening term in the official statement is just a name for one part of that sentence. "Agent architecture" is what shape the helper takes. "Orchestration strategy" is how the helper's steps are arranged. "Evaluate success" is the checking. By the time you reach Part X, you will read the official version and find it says nothing you don't already know.

What you need

  • Python 3.10 or newer, and a text editor. Nothing else to install yet.
  • An Anthropic API key, from console.anthropic.com. You do not need it until Chapter 19, but get it now — discovering you don't have one at hour two of a thirty-hour hackathon is an expensive way to lose a morning.
  • Roughly 20–30 minutes per chapter, more when there's code to type.
  • Willingness to type the code rather than read it. This matters more than it sounds. See below.

How to actually read this

Type the code. Reading code produces a feeling of understanding that evaporates the moment you face a blank file. Typing it — even copying it character by character — produces something that survives. Every implementation in this book is deliberately small enough that typing it costs you two minutes.

Do the failure examples. Each chapter shows you where the thing you just built breaks. Run the broken case yourself and watch it break. Agent engineering is largely the study of failure, and the earlier you develop an appetite for it, the better you will be at Part VIII, which is where this book gets serious.

If you are lost, go back exactly one chapter. The staircase has no gaps by construction. So confusion in Chapter n almost always means something in Chapter n−1 didn't land, not that Chapter n is too hard. This is a diagnostic habit, and it is the same habit Part VIII will teach you to apply to broken agents.

Answers come at the end of the part, not the chapter. The gap is deliberate. Retrieving a half-remembered answer is what builds durable understanding; checking immediately builds only recognition.

A note on honesty

This field moves quickly. Throughout, I will distinguish stable concepts — the agent loop, evaluation, failure analysis, which have been true for years and will stay true — from implementation details like specific model names, API shapes, and library interfaces, which change every few months. When something is genuinely unsettled or contested, I will say so rather than presenting a confident guess as established fact.

You are ready to move on when…
  • You can state the hackathon problem in one plain-English sentence, without using the words "architecture," "orchestration," or "evaluate."
  • You have decided which reading track you're taking.
  • You have Python installed and an API key on the way.

Chapter 1 · Part I · Sprint track

What is a program?

You already know what a program is. This chapter is not really about that. It is about one specific property of programs — a property so reliable that you have never had to think about it — because in seven chapters we are going to break it, and everything difficult about agents flows from that break.

What you will learn
  • What a program is, reduced to its simplest possible description
  • The property called determinism, and why it is a gift you've been taking for free
  • Why deterministic programs are wonderful to debug and terrible at understanding language
  • Your first encounter with the customer-support-routing problem, which will follow us through the entire book

Why this matters

Here is the plot of this entire textbook in one sentence: we are going to take an ordinary program and replace one part of it with something that does not behave like a program at all, and then spend eighty chapters learning to engineer around the consequences.

You cannot feel that plot unless you first have a clear sense of how well-behaved ordinary programs are. So that's this chapter. It's the "before" photograph.

First principles: what a program actually is

Strip away everything and a program is this: a fixed list of instructions that turns an input into an output.

Not "intelligent." Not "thinking." A list of steps, followed exactly, in order, by a machine that has no opinion about them.

The analogy

A program is a recipe. Not a chef — a recipe. The distinction matters.

A chef tastes the sauce and adds salt if it needs it. A recipe says "add one teaspoon of salt," and it says that whether the sauce needs it or not, whether the tomatoes were sweet or sour, whether it's Tuesday or Thursday. Give a recipe the same ingredients and follow the same steps, and you get the same cake. Every single time. Forever.

That reliability is the whole point of a recipe. It is also the whole point of a program. And — this is the part to hold onto — it is exactly what we lose later.

The smallest concrete example

Here is a complete program: 

def add(a, b):
    return a + b

Call add(3, 4) and you get 7. Call it again: 7. Call it a billion times across a thousand machines over ten years: 7, every time. You do not need to test this. You do not need to run it twice to be sure. You know.

Pause on how strange that certainty is. There is almost nothing else in life you can say that about.

The visual model

        INPUT              PROGRAM              OUTPUT
        ─────              ───────              ──────

          3      ──────►   ┌───────────┐   ──────►    7
                           │  a + b    │
          4      ──────►   └───────────┘

And the property we care about, drawn out: 

   run #1     (3, 4)  ──►  ┌─────────┐  ──►  7
                           │         │
   run #2     (3, 4)  ──►  │ PROGRAM │  ──►  7
                           │         │
   run #999   (3, 4)  ──►  └─────────┘  ──►  7

              same                            same
              input                          output
                                            ALWAYS

Same input, same output, always. This is the guarantee you are about to learn the name of — and, eventually, learn to live without.

The technical explanation: determinism, named

Determinism

Plain meaning: the program does the same thing every time you give it the same input.

Technical definition: a computation is deterministic if its output is entirely a function of its input and its starting state — no hidden influences, no variation between runs.

Why it exists as a concept: because it is the assumption underneath every debugging technique you have ever used. "It works on my machine" is only a meaningful complaint in a world where things are supposed to behave identically everywhere.

Determinism buys you three things, and they are worth naming because you are going to miss all three later:

What determinism gives youWhat it means in practice
Reproducible bugs If it broke once, you can make it break again on demand — which is the entire foundation of debugging
Testing that means something A test that passes today passes tomorrow. One run is enough evidence.
Composability you can trust If f is reliable and g is reliable, then g(f(x)) is reliable. Confidence multiplies cleanly.

Keep that third row in mind especially. In Chapter 8 we will find that when a component succeeds only 90% of the time, chaining five of them together gives you 59% — and suddenly "composability" becomes something you have to engineer for rather than assume.

Common misconceptions

"Programs are complicated things"

Large programs are large, but they are not made of complicated stuff. They are made of enormous numbers of simple, deterministic steps. A million-line codebase is a million small certainties stacked up. The complexity is in the arrangement, never in the individual pieces — which is a theme that returns when we start arranging agent components in Part IV.

"Random numbers break determinism"

They don't, quite. random.random() in Python is pseudo-random: it's a deterministic formula that produces random-looking numbers from a starting value called a seed. Fix the seed and you get the identical sequence every time. This is why random.seed(42) makes experiments reproducible, and it is a trick we will reach for again in Chapter 50 when we try — and partly fail — to make agents reproducible.

"A program that reads from a database isn't deterministic"

The program still is; its inputs changed. This is a useful habit of thought: when something behaves inconsistently, first ask whether the logic varies or whether the inputs do. Most of the time it's the inputs. It is also, as it happens, the first question of failure analysis in Part VIII.

Tiny implementation: our first companion

Let's meet the example that will follow us through this whole book.

The problem. A company receives customer support emails. Each one needs to go to the right team: billing, technical, account, or refunds. Right now a person reads each email and forwards it. We would like a program to do it.

The obvious first attempt — and genuinely the right first attempt — is to look for keywords. 

def route_ticket(email_text):
    """Route a support email to a team. Returns a team name."""
    text = email_text.lower()

    if "refund" in text or "money back" in text:
        return "refunds"
    if "password" in text or "login" in text or "error" in text:
        return "technical"
    if "invoice" in text or "charge" in text or "billing" in text:
        return "billing"
    if "account" in text or "profile" in text:
        return "account"

    return "unknown"

Eleven lines. Let's take them apart.

Walkthrough

  • def route_ticket(email_text): — defines a function. One input (the email's text), one output (a team name). This input-to-output shape is the diagram from earlier, made real.
  • text = email_text.lower() — converts to lowercase so that "Refund", "REFUND", and "refund" all match. A tiny bit of normalisation: reshaping messy input into a predictable form before working with it. Remember this idea; it comes back constantly.
  • if "refund" in text … — checks whether that substring appears anywhere. Note the order: refunds is checked first, so an email containing both "refund" and "charge" routes to refunds. The order encodes a priority decision, and it was made silently. Silent decisions like this one are where bugs live.
  • return "unknown" — the fallback when nothing matched. Having an explicit "I don't know" is better engineering than guessing, and it will matter enormously when we start measuring things in Part VII.

Now trace it by hand. Email: "Hi, I forgot my password and can't log in." 

   text = "hi, i forgot my password and can't log in."

   check "refund"     → not present    ✗
   check "money back" → not present    ✗
   check "password"   → PRESENT        ✓  →  return "technical"

   result: technical                    ← correct

It works. And — critically — it will work identically forever. Run it a thousand times on that email and you get "technical" a thousand times. That is determinism, doing its job.

Where it breaks

Now try this email:

"Hey — I was charged twice for the same thing last month and I'd like my money back please." 

   check "refund"     → not present    ✗
   check "money back" → PRESENT        ✓  →  return "refunds"

   result: refunds                      ← arguably correct!

Lucky. We caught it because someone thought to add "money back" to the list. Now try this one:

"I've been billed for a subscription I cancelled in March. Can you sort this out?" 

   check "refund"     → not present    ✗
   check "money back" → not present    ✗
   check "password"   → not present    ✗
   check "login"      → not present    ✗
   check "error"      → not present    ✗
   check "invoice"    → not present    ✗
   check "charge"     → not present    ✗   ("billed" ≠ "charge")
   check "billing"    → not present    ✗   ("billed" ≠ "billing")
   check "account"    → not present    ✗
   check "profile"    → not present    ✗

   result: unknown                      ← a human would say refunds

The word "billed" is not the word "billing." The program cannot see that they are related, because it does not know what words mean — it only knows whether one string appears inside another.

Notice something important, though: it fails the same way every time. That is not a small consolation. It means you can reproduce the bug instantly, reason about it precisely, and know with certainty when you've fixed it. Determinism makes failure legible.

The improvement — and why it can't work

The obvious fix is more keywords: 

    if any(word in text for word in
           ["invoice", "charge", "charged", "billing", "billed",
            "payment", "paid", "subscription", "receipt"]):
        return "billing"

Better. And now try: "You've taken money from my card for something I don't remember signing up for." No keyword matches. Add "taken money," "my card." Then someone writes "there's a mystery transaction on my statement." Add those too.

You can see where this goes. English has an effectively unlimited number of ways to express "you charged me and I'm unhappy about it." You cannot enumerate them. Not because you aren't trying hard enough — because the set is not finite.

The gap this book exists to fill

A deterministic program can only recognise what you explicitly told it to recognise. That is simultaneously its greatest strength — total predictability — and the exact reason it cannot handle language. Every remaining chapter of this book is, in one way or another, about what you get and what you give up when you reach for something that can.

Connection to what comes next

In Chapter 2 we ask how one program talks to another program that lives somewhere else — because the thing that can understand "billed" means "billing" is not going to live on your laptop. Chapter 3 asks what it means for a machine to learn a rule instead of being told it. And Chapter 4 introduces the specific machine we'll be using.

By Chapter 8 you will meet the price: that machine is not deterministic. Ask it the same question twice and you may get two different answers. Everything listed in the table above — reproducible bugs, meaningful tests, composable confidence — is put at risk. Chapters 43 through 58 are essentially a long campaign to win back as much of it as possible.

Connection to the hackathon

This looks distant from Track 1, but it is closer than it appears.

The system you will build is itself a program. Parts of it will be rigidly deterministic — the runner that executes agents, the evaluator that scores them, the code that records what happened. Other parts will be non-deterministic: the component that proposes an agent design, the component that diagnoses failures.

Knowing which parts are which is a core engineering skill, and it separates good submissions from fragile ones. If your evaluator is accidentally non-deterministic, your improvement curve is measuring noise and you will not know it. If your generator is accidentally deterministic, it produces the same architecture for every task and your system does not generalise. Both are real failure modes. Both are avoidable if you can tell the two kinds of component apart — which starts here.

Mental model to remember

A program is a promise: same input, same output, always. Agents break that promise — and everything hard about them follows from the break.

Mini quiz

1. A program reads today's date and prints a greeting that differs on weekends. Is it deterministic? Explain your reasoning in terms of inputs.

2. Our router checks "refund" before "charge." Write an email where that ordering produces a debatable result, and say which team you'd argue for.

3. You add fifty more keywords and accuracy improves from 61% to 68%. Why should you be suspicious of continuing down this path — and what would you expect the curve to do?

4. Someone claims their program is broken because "it gives different answers each run." Name two possible causes that have nothing to do with the logic being wrong.

Practical exercise

Type route_ticket into a file and run it. Then write five real-sounding support emails that it routes incorrectly — not nonsense inputs, but things a genuine customer might plausibly write.

For each one, write a single sentence naming why it failed. You will find the reasons fall into a small number of recognisable groups: a synonym you didn't list, a phrasing with no keyword at all, an email covering two topics at once.

Keep this file. In Chapter 89 you will hand these exact examples to a system that fixes them without your help — and you will already know what makes each one hard. You have just written your first test set, which is a term you will meet properly in Chapter 52.

You are ready to move on when…
  • You can explain determinism to someone else without using the word "deterministic."
  • You can say precisely why the keyword router fails on "I've been billed" — and why adding keywords is not a real fix.
  • You understand that the router's failure being consistent is a feature, not just a curiosity.
  • You have five failing emails written down in a file.
