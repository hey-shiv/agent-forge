Front matter

How to Use This Textbook

What the staircase is made of, where it ends, and how to climb it without falling off.

This book takes you from "what is a computer program?" to building a system that designs, tests, and improves AI agents by itself. It makes one promise, and the whole structure depends on it: you will never meet a word before you have met the problem that word solves.

Where we are going

Here is the destination, in its official words — currently intimidating, and by Part XIII it will not be:

The track statement

"Build a system that can design, test, and improve specialized agents for tasks it has never seen before. Given only a goal, available tools, and a way to evaluate success, your system should generate an agent architecture, run the agent, analyze where it fails, and iteratively improve its prompts, tools, memory, or orchestration strategy."

Now the same thing with every intimidating word removed:

The same thing, in plain English

You will build a program that you hand three things to: a description of a job, a box of tools, and a way of checking whether the job got done properly. Your program then writes its own helper to do that job, tries it out, notices what went wrong, fixes the specific thing that went wrong, and tries again — getting better each round.

That is the entire competition. Every frightening term in the official statement is a name for one part of that sentence. "Agent architecture" is what shape the helper takes. "Orchestration strategy" is how the helper's steps are arranged. "Evaluate success" is the checking.

Part I

The Absolute Foundations

Programs, determinism, the wall that rule-based systems hit, and the strange machine we bring in to get past it.

What you will learn in this part
  • What a program is, reduced to its simplest description — and the property called determinism you have been getting for free
  • Exactly where rule-based programs hit a wall, felt rather than asserted
  • What machine learning is, what a model is, and what "learning" actually means mechanically
  • What an LLM receives, what it returns, and why its answers vary
  • What a prompt is, what context is, and how to get output your code can trust

1.1 · What is a program?

Strip everything away and a program is this: a fixed list of instructions that turns an input into an output. Not intelligent. Not thinking. A list of steps, followed exactly, by a machine with no opinion about them.

The analogy. A program is a recipe — not a chef. The distinction is the whole point. A chef tastes the sauce and adds salt if it needs it. A recipe says "add one teaspoon of salt," and says it whether the sauce needs it or not, whether the tomatoes were sweet or sour, whether it is Tuesday or Thursday. Same ingredients, same steps, same cake. Every time. Forever.

Here is a complete program:

def add(a, b):
    return a + b

Call add(3, 4) and you get 7. Call it a billion times across a thousand machines over ten years: 7, every time. You do not need to test this. You know. Pause on how strange that certainty is — there is almost nothing else in life you can say it about. 

   run #1     (3, 4)  ──►  ┌─────────┐  ──►  7
                           │         │
   run #2     (3, 4)  ──►  │ PROGRAM │  ──►  7
                           │         │
   run #999   (3, 4)  ──►  └─────────┘  ──►  7

              same                            same
              input                          output
                                            ALWAYS
Determinism

Plain meaning: the program does the same thing every time you give it the same input.

Technical definition: a computation is deterministic if its output is entirely a function of its input and starting state — no hidden influences, no variation between runs.

Why it exists as a concept: because it is the assumption underneath every debugging technique you have ever used.

Determinism buys three things. Name them, because you will miss all three later:

What it gives youIn practice
Reproducible bugsIf it broke once, you can make it break again on demand — the entire foundation of debugging
Tests that mean somethingA test passing today passes tomorrow. One run is enough evidence.
Composable confidenceIf f is reliable and g is reliable, g(f(x)) is reliable. Confidence multiplies cleanly.

Hold that third row especially. In §1.6 we find that a component succeeding 90% of the time, chained five deep, gives you 59% — and composability stops being an assumption and becomes something you must engineer.

Common misconception

"Random numbers break determinism." Not quite. random.random() is pseudo-random: a deterministic formula producing random-looking numbers from a starting seed. Fix the seed, get the identical sequence. This is why random.seed(42) makes experiments reproducible — a trick we reach for again in Part VII, where it will only partly work.

1.2 · Where rule-based programs hit the wall

Meet the companion that follows us through this entire book. A company receives support emails; each must go to billing, technical, account, or refunds. The obvious first attempt — and genuinely the right one — is keywords. 

def route_ticket(email_text):
    """Route a support email to a team. Returns a team name."""
    text = email_text.lower()

    if "refund" in text or "money back" in text:
        return "refunds"
    if "password" in text or "login" in text or "error" in text:
        return "technical"
    if "invoice" in text or "charge" in text or "billing" in text:
        return "billing"
    if "account" in text or "profile" in text:
        return "account"

    return "unknown"

text.lower() is normalisation — reshaping messy input into a predictable form before working with it. The order of the checks silently encodes a priority decision: an email containing both "refund" and "charge" routes to refunds. Silent decisions like that are where bugs live. And return "unknown" is an explicit "I don't know," which is better engineering than guessing and will matter enormously once we start measuring things.

Trace it on "Hi, I forgot my password and can't log in."

   check "refund"     → absent    ✗
   check "money back" → absent    ✗
   check "password"   → PRESENT   ✓  →  return "technical"     ← correct

Now: "I've been billed for a subscription I cancelled in March."

   check "refund" ✗   "money back" ✗   "password" ✗   "login" ✗
   check "error"  ✗   "invoice"    ✗   "charge"   ✗   ← "billed" ≠ "charge"
   check "billing"✗   ← "billed" ≠ "billing"
   check "account"✗   "profile"    ✗

   result: unknown          ← a human would say billing or refunds

The word "billed" is not the word "billing." The program cannot see they are related, because it does not know what words mean — only whether one string sits inside another.

Notice, though: it fails the same way every time. That is no small consolation. You can reproduce the bug instantly and know with certainty when it's fixed. Determinism makes failure legible.

The obvious fix is more keywords — "billed", "charged", "payment", "subscription". Better. Then someone writes "you've taken money from my card for something I don't remember signing up for," and then "there's a mystery transaction on my statement." You can see where this goes. English has an effectively unlimited number of ways to say "you charged me and I'm unhappy." You cannot enumerate them — not because you aren't trying hard enough, but because the set is not finite.

The gap this book exists to fill

A deterministic program recognises only what you explicitly told it to recognise. That is simultaneously its greatest strength — total predictability — and the exact reason it cannot handle language. Everything that follows is about what you gain, and what you give up, by reaching for something that can.

1.3 · Machine learning, and what "learning" actually means

We want a component that maps "I've been billed" to billing without anyone writing that rule. The move is to stop writing rules and start showing examples.

The intuition. Traditional programming: you write the rule, the machine applies it. Machine learning: you supply input–output pairs, and a procedure searches for a rule that fits them. 

   TRADITIONAL PROGRAMMING          MACHINE LEARNING

   rules   ──┐                      data    ──┐
             ├──► [ machine ] ──► answers               ├──► [ machine ] ──► RULES
   data    ──┘                      answers ──┘
                                              (then apply the rules to new data)
Model

Plain meaning: the rule the machine found, frozen into a reusable form — a big pile of numbers plus instructions for using them.

Technical definition: a parameterised function whose parameters were fitted to data by an optimisation procedure.

Tiny example: fit a line to points and the model is two numbers, slope and intercept. Everything else is the same idea with more numbers.

Two words worth separating now, because they are constantly confused. Training is the expensive one-time search for good parameters — weeks, many machines, enormous data. Inference is using the finished model on new input — fast, cheap, repeatable. When you call a language model in this book, you are always doing inference. You are never training anything.

1.4 · What is an API?

The model that understands "billed" means "billing" is far too large to run on your laptop. It lives on someone else's machines. So your program needs to talk to a program somewhere else.

The analogy. An API is a restaurant menu. You do not walk into the kitchen and cook. You look at a list of things you may order, order one in the expected format, and food comes back. You do not know or care how the kitchen works — only the menu and the format. 

   YOUR PROGRAM                                    SOMEONE ELSE'S SERVER
   ────────────                                    ─────────────────────

   build request  ──────── over network ────────►  receive request
   {                                               run the model
     "model": "...",                               (the expensive part)
     "messages": [...]                                    │
   }                                                      ▼
                  ◄─────── over network ─────────  send response
   parse response                                  { "content": "..." }

Three consequences follow immediately, and each one shapes the rest of this book. Calls take time (network latency plus computation — hundreds of milliseconds to many seconds). Calls cost money, per call. And calls can fail for reasons that have nothing to do with your logic: the network drops, the server is overloaded, you exceed a rate limit. A local function call never had these properties. Now every one of your interesting operations does.

1.5 · What an LLM actually is, receives, and returns

A large language model is a model trained on an enormous amount of text to do exactly one thing: given some text, predict what text plausibly comes next.

That is genuinely all. Every impressive thing you have seen an LLM do is that single operation, repeated. It looks like conversation because a plausible continuation of a question is an answer. It looks like reasoning because a plausible continuation of "let's think step by step" is a sequence of steps.

What it actually receives. Not concepts, not meaning — a sequence of tokens. A token is a chunk of text, roughly a short word or word-fragment. "billing" might be one token; "recontextualise" might be four. 

   "I've been billed twice"
            │
            ▼  tokenizer
   ["I", "'ve", " been", " billed", " twice"]
            │
            ▼  model
   probability distribution over EVERY possible next token
            │
   " for"    12.4%
   " and"     8.1%
   " —"       3.2%
   ...        (tens of thousands more)
            │
            ▼  sample one
   " for"

Then the chosen token is appended to the input and the whole process repeats. That loop — predict, sample, append — is how a paragraph gets produced one token at a time.

What it returns is therefore text. Not a Python dictionary. Not a number. Text, which you must then interpret. Remember this when we get to §1.7, because it is the source of an entire category of engineering problems.

Prompt

Plain meaning: everything you send the model — the whole text it reads before writing its continuation.

Why it matters: the prompt is not a command you issue to an obedient machine. It is the situation you place the model in. Change the situation, change what continuation is plausible. This is why prompt wording has effects that feel disproportionate.

Most model APIs organise the prompt into messages with roles. A system message sets standing instructions and persona. User messages are what the person said. Assistant messages are what the model said previously. All of it is concatenated into one sequence before the model sees it — the roles are structure for your benefit, and a hint to the model, not separate channels.

Context window

Plain meaning: the maximum amount of text the model can look at in one call.

Technical definition: the maximum sequence length, in tokens, spanning both your input and the model's output.

Consequence: the model has no memory between calls. None. It remembers a conversation only because you resend the whole conversation every single time. This one fact explains most confusion beginners have about "memory," and we build on it heavily in Part VI.

1.6 · Why the same question gives different answers

Recall that the model produces a probability distribution and then samples from it. Sampling means chance. Ask the identical question twice and you may get two different answers.

A parameter called temperature controls how much. At temperature 0 the model takes the highest-probability token every time — nearly deterministic. Higher temperatures flatten the distribution, making unlikely tokens more reachable, which reads as more varied and creative.

Common misconception

"Temperature 0 makes it deterministic." Nearly, but not exactly. Floating-point arithmetic on parallel hardware does not always sum in the same order, batching on the server varies, and models get updated behind a stable name. Treat temperature 0 as low variance, not as a guarantee. Anything you claim to have measured should be measured more than once.

Now look back at the table in §1.1 and watch all three gifts of determinism come under threat. Reproducible bugs: a failure that appears once may not reappear. Meaningful tests: one passing run is no longer evidence. Composable confidence — this is the severe one: 

   ONE STEP, 90% reliable                     0.90  =  90%

   TWO STEPS chained                   0.90 × 0.90  =  81%

   FIVE STEPS chained                       0.90^5  =  59%

   TEN STEPS chained                       0.90^10  =  35%

Ninety percent sounds excellent until you chain it. An agent taking ten steps, each 90% reliable, finishes correctly about a third of the time. This single arithmetic fact is why Parts VII through XII exist.

Mental model to remember

A program is a promise: same input, same output, always. An LLM breaks that promise — and everything hard about agents follows from the break.

1.7 · Structured output: getting a shape your code can trust

Here is the immediate practical problem. Your router needs a team name — one of four strings. The model returns prose: 

   "Based on the email, this looks like a billing issue, since the
    customer mentions being charged for a cancelled subscription."

Your code cannot use that. You could search the text for the word "billing" — but you have just reinvented keyword matching, complete with all its failures, on top of a far more expensive component. You need the model to return a shape.

Three techniques, in increasing order of reliability.

Ask nicely. "Reply with only one word: billing, technical, account, or refunds." This works most of the time and fails in ways that are annoying rather than obvious — a trailing period, a capital letter, an occasional "I'd say billing."

Ask for JSON. Request a specific structure and parse it. Better, but the model may wrap it in explanation or a markdown fence, so you still need defensive parsing.

Constrain the output. Most modern APIs let you supply a schema — a machine-readable description of the required shape — and enforce that the output conforms. This is the reliable option and the one to reach for. The mechanism for this is the same mechanism that makes tool calling work, which is Part II. 

import json

SYSTEM = """You route customer support emails.
Reply with ONLY a JSON object of the form:
{"team": "billing" | "technical" | "account" | "refunds",
 "confidence": 0.0 to 1.0}
No explanation, no markdown fence."""

def route_ticket_llm(client, email_text):
    reply = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=100,
        system=SYSTEM,
        messages=[{"role": "user", "content": email_text}],
    )
    raw = reply.content[0].text
    try:
        parsed = json.loads(raw)
    except json.JSONDecodeError:
        return {"team": "unknown", "confidence": 0.0}   # never trust the shape
    return parsed

Three things to notice. The system message carries the standing instruction — it is identical on every call, so it belongs there rather than glued onto each email. The try/except exists because the model can always violate your format; parsing without a fallback is how production agents die at 3 a.m. And confidence is requested deliberately: an explicit "I am unsure" signal is something you can route to a human, and Part VIII will show you how to measure whether that number means anything.

Run it on the email that defeated the keyword router:

   input:  "I've been billed for a subscription I cancelled in March."

   output: {"team": "billing", "confidence": 0.88}      ← correct

   The model never saw the rule "billed relates to billing."
   It learned that relationship from text, and applied it.

That is the entire reason we accepted the loss of determinism. We traded a guarantee for a capability, and the rest of this book is the engineering discipline required to make that trade pay off.

Part II

From LLM to Tool-Using System

The model can read and write. It cannot do. Closing that gap is the single most consequential move in the book.

2.1 · The problem: a brain in a jar

Our router now understands language. Ask it something else, though, and watch it fall over. 

   you:    "Has customer 4417 been charged twice this month?"

   model:  "I don't have access to your customer records, so I can't
            check that. You'd need to look it up in your billing system."

It is not being unhelpful. It genuinely cannot. Recall exactly what an LLM is from §1.5: a function from text to text. It has no network connection, no filesystem, no database, no clock. It is a brain in a jar — it can think about anything and touch nothing.

Worse, if you push it, it may invent an answer, because a plausible continuation of "has customer 4417 been charged twice" is "yes, on the 3rd and the 17th." The model has no mechanism for distinguishing "recalling" from "generating." That is not a bug; it is what next-token prediction does.

2.2 · The insight that unlocks everything

Here is the move, and it is worth slowing down for because everything after it depends on the shape of this idea.

The model cannot query your database. But your program can. And the model can write text. So: let the model write text that describes a database query it wants performed. Your program reads that description, performs the query itself, and hands the result back to the model as more text.

The model never touches anything. It only ever reads text and writes text — exactly as before. Your ordinary, deterministic, trustworthy Python code does all the touching.

   user question                        user question
        │                                    │
        ▼                                    ▼
   ┌─────────┐                          ┌─────────┐
   │  MODEL  │                          │  MODEL  │ "I need lookup_customer(4417)"
   └─────────┘                          └─────────┘
        │                                    │
        ▼                                    ▼
   "I can't access                      ┌─────────────────┐
    that."                              │  YOUR PYTHON    │ ← actually runs it
                                        │  runs the query │
                                        └─────────────────┘
                                             │  result: {"charges": 2, ...}
                                             ▼
                                        ┌─────────┐
                                        │  MODEL  │ ← sees the real data
                                        └─────────┘

                                         3rd and the 17th."
Tool

Plain meaning: a function in your program that you have described to the model, so the model can ask for it to be run.

Technical definition: a named, schema-described capability exposed to a model, invoked by the model emitting a structured call which the host program executes, returning the result into the model's context.

Related: structured output (§1.7) — tool calling is structured output, used for a specific purpose.

That last line is the connection to hold. In §1.7 we made the model emit JSON matching a schema. A tool call is exactly that, where the schema describes a function's arguments. Same mechanism, enormously larger consequence.

2.3 · What a tool actually looks like

A tool has two halves that must be kept in sync: a description for the model, and an implementation for your program.

# HALF ONE — what the model sees. It never sees the code below.
LOOKUP_CUSTOMER = {
    "name": "lookup_customer",
    "description": (
        "Fetch a customer's billing record by their numeric ID. "
        "Returns charges in the last 90 days, plan name, and account status. "
        "Use when you need facts about a specific customer's billing history."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "customer_id": {
                "type": "integer",
                "description": "The customer's numeric ID, e.g. 4417",
            }
        },
        "required": ["customer_id"],
    },
}

# HALF TWO — what actually runs. Ordinary, deterministic Python.
def lookup_customer(customer_id: int) -> dict:
    row = db.query("SELECT * FROM customers WHERE id = ?", customer_id)
    if row is None:
        return {"error": "no such customer"}
    return {
        "plan": row.plan,
        "status": row.status,
        "charges_90d": row.charges,
    }

The description field is not documentation. It is the only thing the model uses to decide whether to call this function. A vague description produces a tool the model calls at the wrong moments or never at all. This is such a common and such a fixable failure that Part VII devotes a whole section to it — and Part XII makes tool descriptions one of the four things your automated system learns to rewrite.

Common misconception

"The model runs the tool." It never does. The model emits a request — literally structured text saying "I would like lookup_customer with customer_id: 4417." Your program decides whether to honour it, runs it, and returns the result. Every safety property you have depends on this: you are the one executing, and you may refuse.

2.4 · The full cycle, step by step

   STEP 1   You send: messages + tool descriptions
            ────────────────────────────────────────────────►

   STEP 2   Model returns a TOOL CALL, not an answer:
            { type: "tool_use",
              name: "lookup_customer",
              input: { "customer_id": 4417 } }

   STEP 3   YOUR CODE runs lookup_customer(4417)
            → {"plan": "pro", "status": "active", "charges_90d": 2}

   STEP 4   You append TWO messages to the conversation:
              (a) the assistant's tool call
              (b) a tool_result message carrying the return value

   STEP 5   You call the model AGAIN with the longer conversation
            ────────────────────────────────────────────────►

   STEP 6   Model now has the facts, and answers in text.

Step 5 is the one beginners miss. A tool call is not the end of the interaction — it is an interruption in the middle of one. The model paused to ask for something. You must resume it by calling again with the answer included. One tool use costs two model calls. Remember that when we start counting cost and latency in Part VIII.

2.5 · Multiple tools, and the selection problem

Give the model several tools and a new failure appears that did not exist before.

TOOLS = [LOOKUP_CUSTOMER, SEARCH_INVOICES, ISSUE_REFUND, SEND_EMAIL]

Now the model must choose. Sometimes it chooses wrong — calling search_invoices when lookup_customer was needed, or worse, calling issue_refund when it should have gathered information first. This is tool selection failure, and it is one of the named failure classes in Part X. Its usual causes are boringly practical: two descriptions overlap, or one is vague, or a tool that should be a last resort reads like a first resort.

A design principle worth adopting now

Tools that change things (issue a refund, send an email, delete a record) are categorically different from tools that read things. Read-tools can be retried freely. Write-tools cannot. Keep them visibly separate, describe write-tools with explicit preconditions, and consider requiring human confirmation. Part VII returns to this under guardrails.

2.6 · Adding the loop

So far: one tool call, one resumption, done. But consider — "find every customer double-charged last month and email each an apology."

One call cannot do it. You need to search, then for each result look up details, then for each send an email. The number of steps is not known in advance; it depends on what the search returns.

Which forces a loop:

def run(client, user_message, tools, tool_impls, max_turns=10):
    messages = [{"role": "user", "content": user_message}]

    for turn in range(max_turns):
        reply = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=1024,
            tools=tools,
            messages=messages,
        )
        messages.append({"role": "assistant", "content": reply.content})

        # Did it ask for a tool, or is it done?
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return reply                      # stopping condition: no tool wanted

        results = []
        for call in calls:
            fn = tool_impls[call.name]
            try:
                output = fn(**call.input)
            except Exception as e:
                output = {"error": str(e)}    # errors go BACK to the model
            results.append({
                "type": "tool_result",
                "tool_use_id": call.id,
                "content": json.dumps(output),
            })
        messages.append({"role": "user", "content": results})

    raise RuntimeError("hit max_turns without finishing")

Four details in that code carry disproportionate weight.

max_turns. Without it, a model that keeps requesting tools loops forever, burning money. Every loop needs a bound. Always.

The stopping condition. "No tool call in the reply" is the model's way of saying it is finished. The loop's exit is decided by the model, not by your code — which is precisely what makes this different from an ordinary program.

Errors are returned, not raised. When a tool throws, we hand the error text back to the model rather than crashing. This lets the model recover — try different arguments, use another tool, or report the problem. It is the difference between a brittle script and something that copes.

messages grows every turn. This list is the state of the interaction. Everything the system knows lives there, and it is re-sent in full on every call — which means it grows toward the context window and costs more each turn. This observation becomes Part VI.

Mental model to remember

The model never acts. It only ever asks. Your code decides, executes, and reports back — which means every capability, and every safety property, is yours.

Part III

What Is an Agent?

You built one at the end of Part II without being told. Now let's name what you built, and what you didn't.

3.1 · The plain-English version

Imagine asking a chatbot whether your flight is delayed. A normal chatbot tells you what it knows — which is nothing about your flight. An agent looks up the flight, reads the result, decides whether that answered the question, possibly looks up something else, and then tells you.

The difference is not intelligence. It is that the agent decides what to do next based on what it just saw.

Agent

Plain meaning: a system that pursues a goal by repeatedly deciding what to do next, taking an action, looking at the result, and deciding again — until it decides it is finished.

Technical definition: a system in which a model, given a goal and a set of tools, controls its own execution flow — choosing actions and determining termination — rather than following a path fixed in advance by the programmer.

The load-bearing phrase: controls its own execution flow. That is the whole distinction.

3.2 · The spectrum, and where the line actually falls

"Agent" is used loosely. Here is a ladder that makes the distinctions precise.

   1. PROGRAM            input ──► fixed rules ──► output
                         Ch. 1 keyword router. No model at all.

   2. LLM CALL           input ──► model ──► output
                         §1.7 classifier. Model used, path fixed.

   3. CHAIN              input ──► model ──► model ──► output
                         Summarise, then translate. Still fixed.

   4. WORKFLOW           input ──► model ──► [branch] ──► model ──► output
                         YOU wrote the branch conditions.

   5. AGENT              input ──► ┌─ model decides ─┐ ──► output
                                   │       ↕         │
                                   └─ tool result ───┘
                         MODEL decides the path and when to stop.

   6. MULTI-AGENT        several agents, each with own tools,
                         coordinating. Rarely necessary.

The line between 4 and 5 is the one that matters. In a workflow, you wrote if confidence < 0.7: escalate(). The branching is yours; the model just fills in values. In an agent, the model chooses which tool, in what order, how many times, and when to stop.

A diagnostic question that settles almost every case: can you draw the complete flowchart before running it? If yes, workflow. If the shape depends on what the model decides at runtime, agent.

Common misconception

"Every LLM application is an agent." Most are not, and most should not be. Your §1.7 router is a single classification call — level 2. Calling it an agent adds nothing but confusion. Agents are the right answer when the number and order of steps genuinely cannot be known in advance. When they can, a workflow is cheaper, faster, more reliable, and far easier to debug.

3.4 · Stopping conditions deserve their own section

Of the six, stopping is the one beginners underestimate and the one that causes real incidents. An agent has three ways to stop, and a serious system implements all three.

Success. The model emits no tool call, signalling completion. Note the weakness: the model decides it is done. It can be wrong. It can stop early with a partial answer, or declare success having achieved nothing.

Exhaustion. max_turns. A blunt safety net that prevents infinite loops and runaway bills. It should be treated as a failure signal, not a normal exit — if you hit it regularly, something is wrong with your design.

Abort. A budget ceiling, a wall-clock timeout, a repeated identical tool call, or a guardrail violation. This category is what separates a demo from a system, and Part VII builds it out properly.

The failure mode you will meet personally

The most common agent pathology is the loop: the model calls a tool, the result is unhelpful, so it calls the same tool with almost the same arguments, forever. Each iteration costs money and adds tokens to a growing context. Detecting repeated near-identical calls and breaking out is one of the highest-value twenty lines you will ever write.

Agents cost more, take longer, fail in more ways, and are harder to debug. Use one only when you genuinely need one.

4.1 · The calculator agent — small enough to fully understand

Our second companion. The task is deliberately trivial so that nothing distracts from the loop's mechanics: "What is 23 times 47, plus the square root of 1024?" A model can often do this in its head, and often gets it slightly wrong. With a tool it is exact — and more importantly, it requires multiple dependent steps, which is what forces a loop. 

import json, math, anthropic

client = anthropic.Anthropic()

def calculate(expression: str) -> dict:
    """Evaluate a arithmetic expression. Deterministic, no model involved."""
    allowed = {"sqrt": math.sqrt, "abs": abs, "round": round, "pow": pow}
    try:
        value = eval(expression, {"__builtins__": {}}, allowed)
        return {"result": value}
    except Exception as e:
        return {"error": f"could not evaluate: {e}"}

CALCULATE_TOOL = {
    "name": "calculate",
    "description": (
        "Evaluate a single arithmetic expression and return the numeric result. "
        "Supports + - * / ** and the functions sqrt, abs, round, pow. "
        "Pass ONE expression at a time, e.g. '23 * 47' or 'sqrt(1024)'."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "expression": {"type": "string", "description": "e.g. '23 * 47'"}
        },
        "required": ["expression"],
    },
}

Note the description does real work: it names the supported functions, and it says one expression at a time. Without that last sentence the model tends to send 23 * 47 + sqrt(1024) as a single string, which works here but hides the multi-step behaviour we are trying to observe. Tool descriptions shape behaviour. Keep noticing this.

Now the loop — the same skeleton as §2.6, tightened:

def run_agent(user_message, tools, impls, max_turns=8):
    messages = [{"role": "user", "content": user_message}]
    trace = []                                    # ← we will need this in Part IX

    for turn in range(max_turns):
        reply = client.messages.create(
            model="claude-sonnet-5", max_tokens=1024,
            tools=tools, messages=messages,
        )
        messages.append({"role": "assistant", "content": reply.content})

        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            text = "".join(b.text for b in reply.content if b.type == "text")
            return {"answer": text, "turns": turn + 1, "trace": trace}

        results = []
        for c in calls:
            try:
                out = impls[c.name](**c.input)
            except Exception as e:
                out = {"error": str(e)}
            trace.append({"turn": turn, "tool": c.name,
                          "input": c.input, "output": out})
            results.append({"type": "tool_result", "tool_use_id": c.id,
                            "content": json.dumps(out)})
        messages.append({"role": "user", "content": results})

    return {"answer": None, "turns": max_turns, "trace": trace,
            "error": "exhausted"}

Now break it

Try: "What is the square root of negative sixteen?"

Two fixes, and the difference between them is instructive.

# FIX 1 — make the error actionable (a TOOL change)
    except ValueError:

                         "say so rather than retrying."}

A small addition with an outsized effect: ask the model to state its reasoning before each action.

ReAct

Plain meaning: an agent that says why before it does, and says what it learned after.

Technical definition: an architecture interleaving explicit reasoning traces with tool actions and observations in a single loop — Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models (2022).

Why it works: partly the model conditions on its own stated reasoning; partly — and for you, more importantly — you can now read why it went wrong. It converts an opaque failure into a legible one.

That second benefit is the one to hold. In Part X you will diagnose failures, and an agent that recorded "THOUGHT: I need the customer's plan, so I'll search invoices" tells you instantly that the failure was tool selection, not reasoning. Without it you would be guessing.

The cost is real: extra tokens on every turn, so more money and more latency. ReAct is a trade, not a free upgrade.

5.3 · Reflection, and its honest limits

The idea: have the model check its own work.

def reflect(task, draft, max_rounds=2):
    for _ in range(max_rounds):
        critique = call_model(
            "You are a strict reviewer. List concrete, specific problems "
            "with this answer. If it is genuinely correct and complete, "
            "reply exactly: APPROVED.",
            f"Task: {task}\n\nAnswer: {draft}",
        ).text
        if critique.strip() == "APPROVED":
            return draft
        draft = call_model(
            "Revise the answer to address every point of the critique.",
            f"Task: {task}\n\nAnswer: {draft}\n\nCritique: {critique}",
        ).text
    return draft
Common misconception

"Reflection makes agents smarter." Sometimes. It reliably helps where errors are checkable — code that must compile, JSON that must validate, arithmetic that can be re-derived, constraints that can be re-read. It helps far less where the model's original error came from missing knowledge, because the critic has the same gap. A model confidently wrong about a fact will confidently approve its own wrong answer. Always measure reflection rather than assuming it; you are paying two to three times as much per run for it.

5.4 · Multi-agent, and why to resist it

Multi-agent systems are the most over-reached-for architecture in the field. The intuition "more specialists means better results" imports an assumption from human organisations that does not transfer cleanly, because coordination between agents costs tokens, adds latency, and creates entirely new failure modes — agents duplicating work, contradicting each other, or deadlocking in mutual deferral.

The honest test: use multi-agent only when at least two of these hold.

  • Subtasks need genuinely different toolsets, not just different phrasing
  • Subtasks can run in parallel, so you actually buy latency back
  • Context for the whole task would not fit in one window
  • Different subtasks warrant different models — a cheap one for bulk, an expensive one for judgement

If only one holds, a single agent with more tools is almost always better. Note that this is a claim you should measure rather than take from me — and by Part VIII you will have the harness to do exactly that.

Mental model to remember

Architecture is not a ranking from worse to better. It is a menu of trades between cost, latency, reliability, and adaptability — and the right choice is a function of the failure you are trying to prevent.

6.1 · Separating the three

Confusing them produces designs that cannot work — "just give the agent memory of everything" fails because everything does not fit in the context window, and the window is not negotiable.

6.2 · The context window as a budget

Every turn of an agent loop re-sends the entire conversation. That has an arithmetic consequence people find surprising:

   turn 1:   + tool_call(80) + result(1200)                 =  1,980 tok
   turn 2:   + tool_call(80) + result(1500)                 =  3,560 tok
   turn 3:   + tool_call(80) + result(3000)                 =  6,640 tok
   turn 4:   + tool_call(80) + result(900)                  =  7,620 tok
                                                              ────────
   total input tokens billed across the run:                  20,500

   You paid for the system prompt FIVE TIMES.

An agent's cost is roughly quadratic in turn count, not linear, because each turn re-sends everything before it. This is the single most important cost fact in agent engineering, and it is why Part XIX treats cost as a first-class objective rather than an afterthought.

Three mitigations, each with a real cost of its own:

  • Truncate — drop the oldest turns. Cheap and simple; risks discarding something that mattered.
  • Summarise — replace old turns with a model-written précis. Preserves gist; costs an extra call and loses detail irreversibly.
  • Externalise — write large results to a store, keep only a reference in context, add a tool to fetch them back. Most scalable; adds a tool and a failure mode.

6.3 · Kinds of memory, and what each is for

"Memory" is not one thing. Four distinct capabilities get bundled under the word, and they have different implementations and different failure modes.

KindHoldsExampleTypical store
WorkingThe current task's scratchpad"I have checked invoices, not yet the plan"The messages list
EpisodicSpecific past events"On 3 Sept this customer was refunded"Event log, queried by key
SemanticGeneral facts and knowledge"Pro plans bill on the 1st"Document store + retrieval
ProceduralLearned how-to"For billing disputes, check charges before replying"Prompt text, updated over time

That last row is quietly the most important one in this book. Procedural memory is stored in the prompt. When your automated system in Part XIV "improves the agent's memory," what it usually means concretely is: it writes a lesson learned from failure into the system prompt so the next version starts out knowing it. Memory and prompt are not as separate as they sound.

6.4 · Retrieval, conceptually

Semantic memory needs a way to find relevant facts without loading everything. The standard approach rests on embeddings.

Embedding

Plain meaning: a way of turning a piece of text into a list of numbers, such that texts with similar meanings get similar lists.

Technical definition: a learned mapping from text to a fixed-dimensional dense vector, trained so that semantic similarity corresponds to geometric proximity.

Why it solves our problem: "I've been billed" and "you charged me" share no words, but land near each other in this space. It is a computational answer to exactly the failure that broke our keyword router in §1.2.

   STORING                             RETRIEVING

   doc ──► embed ──► [0.2,-0.7,...]    query ──► embed ──► [0.3,-0.6,...]
                          │                                     │
                          ▼                                     ▼
                    ┌───────────┐                    find nearest vectors
                    │  vector   │ ◄──────────────────────────────┘
                    │   store   │
                    └───────────┘  ──►  the 3-5 closest documents
                                             │

You have met this shape before if you have looked at cover-song retrieval: represent things as vectors, define a distance, return nearest neighbours. The mathematics of "find similar documents" and "find recordings of the same work" is genuinely the same mathematics — which is one reason your music domain will slot into an agent framework more naturally than you might expect.

6.5 · When memory hurts

Common misconception

"More memory always makes the agent better." It frequently makes it worse, in three specific ways worth being able to name.

Pollution. Retrieval returns five documents; two are relevant, three are superficially similar noise. The model now reasons over a context where most of the evidence is misleading. Precision in retrieval matters more than recall here, which is the opposite of the intuition most people bring.

Staleness. A remembered fact was true and is not any more. The customer changed plans; the policy changed in March. Memory with no expiry silently degrades from an asset into a source of confident errors.

Cost. Every retrieved document is tokens on every subsequent turn — and by §6.2, tokens added early are paid for repeatedly. Retrieval that adds two thousand tokens at turn one has added ten thousand billed tokens across a five-turn run.

So: default to no memory. Add it when you can point at a specific failure that memory fixes, and then measure that the fix is real. This is the same discipline the whole book keeps returning to, and Part XI turns it into an algorithm.

Mental model to remember

Context is a hard limit, state is what you track, memory is what you build. And a token added early is a token paid for on every turn that follows.

Part VII

Engineering Reliable Agents

An agent that works once is a demo. An agent that works consistently is an engineered system.

7.1 · Tool design is where most reliability is won or lost

Beginners tune prompts. Experienced engineers fix tools. The reason is that a tool description is the model's only information about when and how to use a capability, so a bad description produces failures that no amount of prompt wording repairs.

Take one tool through three revisions.

# v1 — the version everyone writes first
{"name": "get_data",
 "description": "Gets data.",
 "input_schema": {"type": "object",
                  "properties": {"q": {"type": "string"}}}}

The model has no idea what data, when to use it, or what q should look like. It will call this at random moments with unpredictable arguments.

# v2 — names the thing
{"name": "search_invoices",
 "description": "Search invoices by customer ID or date range.",
 "input_schema": {"type": "object",
   "properties": {"customer_id": {"type": "integer"},
                  "start_date": {"type": "string"},
                  "end_date":   {"type": "string"}}}}

Better. But: what date format? Is customer_id required? What comes back? What if nothing matches?

# v3 — the version that actually works
{"name": "search_invoices",
 "description": (
   "Search a customer's invoices within a date range. "
   "Use when you need billing history for a SPECIFIC customer whose ID "
   "you already know — call lookup_customer first if you only have a name. "
   "Returns up to 50 invoices, newest first, each with "
   "{id, amount_cents, status, issued_at}. "
   "Returns an empty list if there are no matches — an empty list means "
   "NO INVOICES EXIST, not an error, and you should not retry."),
 "input_schema": {"type": "object",
   "properties": {
     "customer_id": {"type": "integer",
                     "description": "Numeric ID from lookup_customer"},
     "start_date": {"type": "string",
                    "description": "ISO date, e.g. 2026-01-15"},
     "end_date":   {"type": "string",
                    "description": "ISO date, inclusive"}},
   "required": ["customer_id"]}}

Five things v3 does that v2 did not, each preventing a specific observed failure:

  • States a precondition ("call lookup_customer first") — prevents calling with a name instead of an ID
  • Describes the return shape — the model can plan its next step before seeing the result
  • Gives the date format by example — eliminates format guessing, the most common argument error
  • Explains the empty case explicitly — prevents the retry loop from §4.1
  • Marks what is required — prevents omitted arguments

Keep this progression in mind. In Part XII, "rewrite the tool description" is one of the four levers your automated system pulls — and what it is doing is exactly this v1→v3 journey, driven by observed failures rather than by your intuition.

7.2 · Failure handling that lets the agent recover

def safe_call(fn, args, timeout=20, retries=2):
    """Run a tool so that no failure mode can hang or crash the loop."""
    for attempt in range(retries + 1):
        try:
            return {"ok": True, "data": run_with_timeout(fn, args, timeout)}

        except TransientError as e:              # network blip, rate limit
            if attempt < retries:
                time.sleep(2 ** attempt)          # exponential backoff
                continue
            return {"ok": False,
                    "error": f"Service unavailable after {retries+1} tries. "
                             f"Do not retry; report this to the user."}

        except ValidationError as e:              # bad arguments — model's fault
            return {"ok": False,
                    "error": f"Invalid arguments: {e}. "
                             f"Check the schema and call again with corrections."}

        except TimeoutError:
            return {"ok": False,
                    "error": f"Timed out after {timeout}s. Try a narrower "
                             f"query — for example a shorter date range."}

The crucial design decision is that every error message tells the model what to do next. Compare "Invalid arguments: expected integer" with "Invalid arguments: expected integer. Check the schema and call again with corrections." The first invites a retry loop; the second directs a fix. Your error strings are prompts. Write them as such.

Note also the distinction between error types. Transient errors are retried by your code with backoff, because retrying is genuinely the right response and the model does not need to be involved. Validation errors are returned to the model, because only the model can fix its arguments. Getting this split right removes a whole class of wasted turns.

7.3 · Guardrails

Three layers, and the ordering matters because each is cheaper than the one after it.

LayerChecksExample
InputBefore the agent startsReject over-long input; strip secrets; refuse out-of-scope requests
ActionBefore each tool executesRefunds over $500 need human approval; no writes to production before review
OutputBefore returningAnswer cites a real invoice ID; no leaked internal data; conforms to schema
 
def guarded_execute(call, impls, budget):
    if call.name in WRITE_TOOLS and not budget.human_approved:
        return {"error": "This action modifies data and needs approval. "
                         "Explain what you intend to do and why."}
    if budget.spent_usd > budget.limit_usd:
        raise BudgetExceeded(f"${budget.spent_usd:.2f} > ${budget.limit_usd}")
    return impls[call.name](**call.input)
Common misconception

"I'll put the guardrail in the prompt." Prompt instructions are requests, not constraints. "Never issue a refund over $500" will be followed most of the time and violated some of the time, and you cannot predict which. If a rule genuinely must hold, enforce it in code, where §1.1's determinism still applies. Prompts shape behaviour; code guarantees it.

This section is short and it is the hinge of the entire second half of the book. Everything in Parts IX through XIV depends on having recorded what happened.

  • Token counts, input and output, per call
  • Wall-clock time per call and for the whole run
  • The agent specification used — which prompt, which tools, which architecture
  • The final outcome and whether it was correct

7.5 · Reliability as a measured property

Recall §1.6: run the same input twice, get different answers. Which means a single test tells you almost nothing.

   Agent A, one run:    ✓            "it works!"
   Agent A, ten runs:   ✓✓✗✓✓✗✓✗✓✓    70% — a very different system

   Agent B, ten runs:   ✓✓✓✓✓✓✓✓✓✗    90%

   Same "it works" demo. Wildly different systems.
Reliability

Plain meaning: how often the agent succeeds when you run it repeatedly on the same input.

Technical definition: the success rate under repeated independent trials of an identical task, distinct from accuracy, which is the success rate across different tasks.

Why the distinction is not pedantry: an agent can be 80% accurate across a hundred different tasks while being wildly unreliable — succeeding on the easy 80% every time and the hard 20% never. Or it can be uniformly 80% reliable on every task. These need completely different fixes, and one number cannot tell them apart.

This is a hackathon-scored metric, listed separately from accuracy, and most entrants will conflate the two. Measuring them separately — the same task run five times, versus a hundred tasks run once — is cheap and it is exactly the kind of rigour that distinguishes a submission.

Mental model to remember

Prompts shape behaviour; code guarantees it. Error messages are prompts. And a system you did not instrument is a system you cannot improve.

Part VIII

Evaluation

Turning "it seems better" into a number you can defend. Nothing after this point works without it.

8.1 · Why this is the hard part

In ordinary software, correctness is usually obvious: the function returns 7 or it does not. With agents, "correct" is frequently a judgement — was that summary good? was that routing right when the email raised two issues? was that answer complete?

And you cannot skip it. Your entire hackathon submission is a loop that improves an agent, and improvement is defined relative to a measurement. A broken evaluator does not just give you wrong numbers; it makes your improvement loop optimise toward the wrong thing while reporting success. Of all the components you will build, this is the one whose failure is hardest to notice.

8.2 · Test sets, and the discipline around them

Test set

Plain meaning: a fixed collection of tasks where you already know the right answer.

Technical definition: a held-out sample of task instances with ground-truth labels, used to estimate performance on unseen inputs.

Tiny example: fifty support emails, each labelled with the team it should go to.

Three splits, three purposes. Mixing them is the most common self-inflicted wound in applied ML.

SplitUsed forHow often you may look
DevelopmentDebugging, iterating, reading failures in detailConstantly
ValidationChoosing between candidate agentsEach improvement round
TestThe number you reportOnce, at the very end
Benchmark overfitting, and why it will bite you specifically

Your system runs many improvement rounds against the same evaluation set. After twenty rounds of "change something, keep it if the number goes up," you have fitted your agent to the quirks of those particular examples. The number rises; genuine capability does not. This is overfitting, and an automated improvement loop does it faster and more thoroughly than a human ever could — because it is tireless and it has no taste. The defence is a held-out test set the loop never sees, and Part XX makes this concrete.

8.3 · The metrics, with worked arithmetic

Setting: 100 support emails. 30 are genuinely billing. Your agent labels 25 as billing, of which 20 are right.

                    predicted billing    predicted other
   actually billing        20  (TP)           10  (FN)      = 30
   actually other           5  (FP)           65  (TN)      = 70
                        ────────           ────────
                            25                 75            = 100

Accuracy — of everything, how much did you get right?

   (TP + TN) / total  =  (20 + 65) / 100  =  0.85   →  85%

True but potentially misleading. Label everything "other" and you score 70% while being useless for billing. Accuracy flatters you whenever classes are imbalanced.

Precision — when you said billing, how often were you right?

   TP / (TP + FP)  =  20 / 25  =  0.80   →  80%

Recall — of all real billing emails, how many did you catch?

   TP / (TP + FN)  =  20 / 30  =  0.67   →  67%

They trade off, and which one you care about is a business decision, not a technical one. Route aggressively to billing and recall rises while precision falls. For support routing, a missed billing email (low recall) annoys a customer; a misrouted one (low precision) wastes an agent's minute. For a medical screen, recall dominates. Decide deliberately.

F1 — their harmonic mean, when you need one number:

   2 × (P × R) / (P + R)  =  2 × (0.80 × 0.67) / (0.80 + 0.67)  =  0.73

The harmonic mean is used rather than the ordinary average because it punishes imbalance: precision 1.0 with recall 0.0 gives F1 = 0, whereas a plain average would give a respectable-looking 0.5 for a system that never fires.

8.4 · The four hackathon metrics, defined precisely

MetricDefinitionHow to measure it
AccuracyFraction of different tasks solved correctlyRun the whole test set once
ReliabilityFraction of successes on the same task repeatedRun a subset 5× each; report mean and variance
CostDollars per taskSum tokens × price across every call in the trajectory
SpeedSeconds per taskWall clock, end to end; report median and p95

Report p95 latency alongside the median, not instead of it. An agent with a 2-second median and a 45-second p95 has a serious problem — probably a loop pathology on a subset of inputs — that the median hides completely. Judges notice this kind of care.

8.5 · LLM-as-judge

Some outputs have no ground-truth string. "Was this summary good?" has no lookup table. So you ask a model.

JUDGE = """Score the agent's answer against the reference on three criteria.
For each, give an integer 1-5 and a one-sentence justification.

  correctness  — are the facts right?
  completeness — does it address the whole question?
  grounding    — is every claim supported by the retrieved evidence?

Return JSON only:
{"correctness": n, "completeness": n, "grounding": n, "why": "..."}"""

Powerful, and genuinely dangerous. Four known biases, all documented and all real:

  • Position bias — comparing two answers, judges favour whichever came first. Mitigate by evaluating both orderings and averaging.
  • Length bias — longer answers score higher, largely independent of quality.
  • Self-preference — a model tends to rate its own outputs above others'.
  • Anchoring — showing the judge a score to "verify" pulls it toward that score.

The essential discipline: validate your judge against human labels before trusting it. Hand-label thirty examples yourself, run the judge on the same thirty, and measure agreement. If the judge agrees with you 60% of the time, its scores are noise and every improvement built on them is imaginary. This takes an hour and it is the single highest-leverage hour in an evaluation-heavy project.

8.6 · Building the harness

@dataclass
class EvalCase:
    id: str
    input: Any
    expected: Any
    tags: list[str]          # ← "multi_issue", "no_keyword", "ambiguous"

@dataclass
class EvalResult:
    accuracy: float
    reliability: float
    mean_cost_usd: float
    median_seconds: float
    p95_seconds: float
    per_case: list[dict]     # ← every case, kept for failure analysis
    trajectories: list[Trajectory]

def evaluate(agent, cases, repeats=1) -> EvalResult:
    per_case = []
    for case in cases:
        outcomes = []
        for _ in range(repeats):
            traj = agent.run(case.input)
            ok = score(traj.final_answer, case.expected)
            traj.success = ok
            outcomes.append({"ok": ok, "traj": traj})
        per_case.append({
            "case": case,
            "outcomes": outcomes,
            "accuracy": mean(o["ok"] for o in outcomes),   # reliability if repeats>1
        })
    return aggregate(per_case)

Two design choices deserve comment. repeats is what lets one harness measure both accuracy (repeats=1 across many cases) and reliability (repeats=5 on a subset) — the distinction from §7.5, made operational. And tags exists because in Part X you will want to ask "what do the failures have in common?", and pre-tagged cases turn that from a research project into a groupby.

Mental model to remember

A score tells you WHAT happened. It never tells you WHY. Everything from here to the end of the book is about closing that gap.

Part IX

Trajectories

The complete record of what an agent did. Learning to read one is the core diagnostic skill.

9.1 · What a trajectory is

Trajectory

Plain meaning: the full story of one agent run — every thought, every tool call, every result, in order.

Technical definition: the ordered sequence of states, actions, and observations produced by one execution, together with the metadata needed to interpret it.

Why the word exists: because "the output" is one point, and you cannot debug a point. You need the path.

A score says the run failed. A trajectory says where it failed. That is the whole difference, and it is why §7.4 insisted on recording everything.

9.2 · Reading one, annotated

A support agent, on the email: "I was charged twice for my Pro plan in March and I want a refund."

   ═══ TRAJECTORY run_8841 · agent v2 · FAILED ═══════════════════

   GOAL   route + resolve: "charged twice for Pro plan in March,
                            want a refund"

Now read it as a diagnostician rather than a spectator. The symptom is a wrong answer at turn 3. But turn 3 is reasonable given what the agent knew — an empty list genuinely does suggest no charges. The reasoning was sound; the premise was false.

Walk backwards to find where the premise broke:

   turn 3   wrong answer          ← SYMPTOM
      ▲
   turn 2   empty result          ← because customer_id=0 is not real
      ▲
   turn 1   lookup failed         ← passed a description, not an address
      ▲
   turn 0   called without an ID  ← ROOT CAUSE: no procedure for
                                    "get identity before querying"

The root cause is at turn 0, three steps before the visible failure. This backwards walk is the single most transferable skill in this book, and it maps exactly onto the reading advice in the front matter: when lost at step n, the problem is usually at n−1.

9.3 · Three fixes, three different levers

Given that root cause, there are three genuinely different repairs — and choosing between them is the skill Part XII formalises.

LeverChangeGeneralises to
PromptAdd: "Always obtain the customer ID before querying invoices."This one agent, this one task
ToolAdd to search_invoices description: "Requires a real ID from lookup_customer — never guess or pass 0."Every agent that ever uses this tool
OrchestrationSwitch to planner–executor so identity resolution is an explicit first stepEvery task with a required setup phase

All three would fix this run. They differ in blast radius, and a good improvement system reasons about that rather than reaching for the prompt every time — which is the lazy default and the reason most naive self-improvement loops plateau.

Notice also a second, independent bug this trajectory exposes: customer_id=0 was accepted and silently returned an empty list. A validation guardrail rejecting nonsensical IDs would have surfaced the real problem at turn 2 instead of manufacturing a plausible-looking wrong answer. Trajectories routinely reveal more than the failure you went looking for.

Mental model to remember

The failure you see is rarely the failure that happened. Walk backwards from the symptom until you find the first step that was wrong — that is the one worth fixing.

Failure Analysis

The deepest part of this book. The gap between "it failed" and "here is why, and here is what to change."

10.1 · Symptom, cause, root cause

Three words that get used interchangeably and must not be.

LevelQuestionrun_8841
SymptomWhat did you observe?Wrong answer: "no duplicate charges"

Fixing the immediate cause gives you a patch — "if the list is empty, say so" — that fails differently next week. Fixing the root cause prevents the class. The whole value of your hackathon system rests on it reaching level three rather than stopping at level two, and most naive implementations stop at level two.

10.3 · Architecture failure, and how to recognise it

This class deserves special attention because it is the one people miss for longest, wasting days on prompts that cannot possibly help.

Recall the multi-issue email from the very beginning: "I was charged twice AND I can't log in." Your router emits exactly one label. It is not confused. It is not badly prompted. It is structurally incapable of the correct output, which is two labels. 

   PROMPT FAILURE                    ARCHITECTURE FAILURE

   The agent COULD produce the       The agent CANNOT produce the
   right answer but didn't.          right answer at all.

   Test: does a better prompt        Test: does the correct output
   fix it on this example?           even fit the output shape?

   Fix: change words.                Fix: change the shape.
                                     Words will never work.

The diagnostic question is beautifully simple: could this architecture, on its very best day, produce the correct answer? If no, stop tuning prompts. Nothing you write in English will make a single-label classifier emit two labels.

10.4 · Clustering: from a pile of failures to a diagnosis

Thirty-eight failures out of a hundred. Reading all thirty-eight individually is slow and, more importantly, does not tell you what to fix first. Group them.

def cluster_failures(results):
    """Group failures by observable signature, so counts become evidence."""
    buckets = defaultdict(list)
    for r in results:
        if r["ok"]:
            continue
        t = r["traj"]
        signature = (
            t.steps[-1].tool if t.steps else "no_tool_used",
            "errored"    if any(s.error for s in t.steps)      else "clean",
            "exhausted"  if len(t.steps) >= t.max_turns        else "finished",
            tuple(sorted(r["case"].tags)),
        )
        buckets[signature].append(r)

    return sorted(buckets.items(), key=lambda kv: -len(kv[1]))

Part XI

Self-Improvement

The central distinction of this book: retrying is not improving.

11.1 · Retry versus improvement

   RANDOM RETRY                        DIAGNOSIS-DRIVEN IMPROVEMENT

   run  ──►  failed?                   run  ──►  failed?
     ▲          │                        │          │
     │          ▼                        │          ▼
     │      try again                    │     cluster failures
     │      (same thing,                 │          │
     │       or a random                 │          ▼
     └────── variation)                  │      diagnose root cause
                                         │          │
   Expected gain per round:              │          ▼
   ~0 beyond sampling noise.             │      choose the LEVER
                                         │          │
   Cost per round: full.                 │          ▼
                                         └───── make ONE targeted change

                                       Expected gain: real and explainable.

A judge can tell these apart in about ninety seconds, and the tell is whether your system can say why it made each change. "Round 2: rewrote the prompt" is a retry with extra steps. "Round 2: 45% of failures were multi-issue emails that a single-label architecture cannot express, so switched to decompose-then-classify" is engineering.

Common misconception

"Retrying counts as self-improvement." It does not, and the reason is precise: retrying explores the same distribution again. Occasionally you get a better sample, which looks like progress and is actually variance. Real improvement changes the distribution — after the change, the agent is a different agent that is better on the failure class you targeted. If you cannot name what changed and why, you have not improved anything.

11.2 · The improvement loop

def improve(spec, cases, rounds=5):
    history = [], best = None

    for r in range(rounds):
        result = evaluate(build_agent(spec), cases, repeats=3)
        history.append({"round": r, "spec": spec, "result": result})

        if best is None or result.accuracy > best["result"].accuracy:
            best = history[-1]                     # keep the champion

        if r == rounds - 1:
            break

        clusters   = cluster_failures(result.per_case)
        diagnosis  = analyze(spec, result, clusters)      # §10.5
        candidates = propose(spec, diagnosis, n=3)        # §11.3

        scored = []
        for cand in candidates:
            quick = evaluate(build_agent(cand), validation_subset, repeats=2)
            if regression_check(quick, result):           # §11.4
                scored.append((quick.accuracy, cand))

        if not scored:
            break                                  # nothing beat the incumbent
        spec = max(scored)[1]

    return best, history

Four decisions in that code carry the weight. Champion tracking means a bad round cannot destroy your best result — you always return the best-seen spec, never the last one. Multiple candidates per round hedge against a single bad proposal. Cheap screening on a validation subset avoids paying full evaluation cost for obviously-worse candidates. And the regression check is what stops the loop from trading one failure class for another.

11.4 · Regression testing

The characteristic failure of improvement loops: round 3 fixes multi-issue emails and quietly breaks simple ones. Aggregate accuracy rises by two points, so the loop declares victory, and a whole capability has silently died. 

def regression_check(new, old, tolerance=0.02):
    """Accept a candidate only if it improves overall AND breaks nothing
    that previously worked."""
    if new.accuracy < old.accuracy:
        return False

    previously_passing = {c["case"].id for c in old.per_case if c["accuracy"] == 1.0}
    now_failing = {c["case"].id for c in new.per_case
                   if c["accuracy"] < 1.0 and c["case"].id in previously_passing}

    broken_fraction = len(now_failing) / max(len(previously_passing), 1)
    if broken_fraction > tolerance:
        log(f"REJECTED: broke {len(now_failing)} previously-passing cases")
        return False
    return True

A small tolerance is allowed rather than demanding zero, because §1.6's non-determinism means a case can flip without anything having genuinely changed. Demanding perfect preservation would reject good candidates for noise. Two percent is a starting point you should tune against your own measured variance — a point Part XX returns to.

Part XII

The Four Improvement Levers

Prompt, tools, memory, orchestration. Knowing which to pull is the skill.

12.1 · The mapping

   FAILURE PATTERN                    LEVER              BLAST RADIUS

   ignores an instruction        ──►  PROMPT             this agent
   wrong output format           ──►  PROMPT             this agent
   correct data, bad conclusion  ──►  PROMPT             this agent

   picks the wrong tool          ──►  TOOLS              every agent
   malformed arguments           ──►  TOOLS              using that tool
   no tool exists for the need   ──►  TOOLS

   forgets earlier findings      ──►  MEMORY             this agent
   repeats work already done     ──►  MEMORY
   uses a stale fact             ──►  MEMORY

   wrong order of operations     ──►  ORCHESTRATION      the whole design
   cannot express correct output ──►  ORCHESTRATION
   loops / exhausts turns        ──►  ORCHESTRATION

12.2 · Lever one: prompts

Cheapest, fastest, most over-used. Effective prompt changes are specific and behavioural:

# WEAK — a wish
"Be careful and accurate when routing."

# STRONG — a procedure, derived from an observed failure
"""Before choosing a team, check whether the email raises more than one
distinct issue. If it does, list each issue separately, then classify
each one. A billing complaint and a login problem in the same email are
two issues, not one.

If a charge has already posted, the issue is refunds. If it has not yet
posted, it is billing. Check which before deciding."""

The second is longer, and it is not padding — every sentence maps to a failure someone observed. That is what distinguishes prompt engineering from prompt fiddling: each line exists because a specific trajectory demanded it. It is procedural memory (§6.3) written down.

The limit: prompts cannot create capability. No wording makes a single-label output emit two labels, or lets an agent query a database it has no tool for.

12.3 · Lever two: tools

Three sub-levers, in increasing order of cost:

Rewrite a description. Free, and often the highest-value change in the whole system, because it fixes selection and argument failures at once — and it fixes them for every agent that uses the tool, present and future. This is the widest blast radius available for the lowest cost, which is a rare combination and worth exploiting first.

Tighten a schema. Turn a free-text field into an enum and an entire class of argument errors becomes structurally impossible rather than merely discouraged.

Add or remove a tool. Adding grants new capability. Removing is underrated: fewer tools means fewer selection mistakes, and a tool used wrongly more often than rightly is worse than no tool.

12.4 · Lever three: memory

Recall §6.5 — memory frequently hurts. So this lever is used sparingly and always in response to a specific observed pattern:

ObservedChange
Re-fetches the same record repeatedly within a runAdd working-memory cache
Makes the same class of mistake across many runsWrite the lesson into the prompt (procedural)
Needs facts not in the prompt and not tool-fetchableAdd retrieval
Context exhausted on long tasksSummarise or externalise (§6.2)

12.5 · Lever four: orchestration

Most powerful, most expensive, and the only one that can fix an architecture failure. The moves are transitions on §5.1's menu:

   single-shot  ──►  ReAct              when facts must be fetched
   ReAct        ──►  planner-executor   when it wanders
   any          ──►  + reflection       when errors are checkable
   any          ──►  decompose-first    when inputs are compound
   any          ──►  + router           when input classes differ sharply
   ReAct        ──►  single-shot        when the loop was unnecessary  ← don't forget this one

That last transition matters more than people expect. Simplification is a legitimate improvement: an agent that was needlessly looping and now answers in one call is better on cost, latency, and reliability simultaneously. A system that only ever adds complexity is not optimising, it is accreting.

12.6 · Choosing under a budget

Given several viable changes, prefer in this order:

  1. Fixes the biggest cluster — attack the dominant mode first
  2. Widest blast radius per unit cost — tool descriptions win here
  3. Cheapest to run afterwards — free beats 2×, all else equal
  4. Most reversible — a prompt edit is easy to undo; a rearchitecture is not

Which is why "rewrite the tool description" is so often the correct first move: it is free, it is wide, and it is trivially reversible.

Mental model to remember

Four levers, and the diagnosis picks which one. A system that always reaches for the prompt has one lever and three decorations.

Part XV

Agent Specification

To generate agents automatically, an agent must first be data rather than code.

15.1 · Why this abstraction is the keystone

So far your agents have been Python functions. A program cannot easily write, mutate, diff, or version a Python function. So represent an agent as a data structure, and let a builder turn that structure into a runnable thing.

15.3 · The builder

def build(spec: AgentSpec) -> Callable:
    """Turn a specification into something runnable. The ONLY place
    orchestration names become behaviour."""
    impls = {t.name: TOOL_REGISTRY[t.name] for t in spec.tools}
    descriptors = [{"name": t.name, "description": t.description,
                    "input_schema": t.schema} for t in spec.tools]

    runners = {
        "single_shot":        run_single_shot,
        "react":              run_react,
        "planner_executor":   run_planner_executor,
        "router":             run_router,
        "reflection":         run_reflection,
        "decompose_classify": run_decompose_classify,
    }
    runner = runners[spec.orchestration]

    def agent(task_input):
        return runner(spec, descriptors, impls, task_input)
    return agent

Adding a new architecture means adding one entry to that dictionary and one function. Your generator's option space grows without touching the generator — which is exactly the kind of extensibility that makes a system feel designed rather than assembled.

Part XVIII

The Music Domain

Your own research problem, treated as one domain among several — the hardest test of a general system.

18.1 · The problem, stated plainly

Two recordings of the same song. Different singer, different key, different tempo, different decade, different instruments. A human recognises them instantly. The task is to make a system rank recordings so that other performances of the same underlying composition appear at the top.

Vocabulary, because the dataset uses it: a work is the abstract composition (what a songwriter wrote); a performance is one recording of it; all performances of one work form a clique. Retrieval succeeds when a query pulls its clique-mates to the top.

Why it is hard, and why the obvious approaches fail:

What changes between versionsWhat it breaks
Key — sung lower to fit a voiceEvery absolute pitch is wrong
Tempo — a ballad taken at double timeNothing lines up in time
Instrumentation — orchestral vs solo guitarTimbre is unrecognisable
Structure — verse dropped, solo addedSections appear, vanish, reorder

Audio fingerprinting (the Shazam family) matches exact spectral landmarks, so it identifies the same recording through noise and fails completely on a re-performance. What survives a cover is the relative harmonic movement — the shape of the chord progression, independent of key and tempo.

18.2 · The capabilities this domain needs

Ask the question Part XIV trains you to ask: what would an agent need to solve this? Not "what is the best algorithm" — what tools must exist.

Why chroma solves the key problem so cleanly

Doubling a frequency raises a note one octave, and musically all octaves of "A" serve the same harmonic function. Fold every octave onto twelve pitch classes and a track becomes an (n_frames, 12) matrix with timbre largely washed out. Then transposing music up three semitones is exactly a circular shift of those twelve columns — and since there are only twelve possible shifts, you can try all of them and keep the best. A problem that sounds hard becomes a loop over twelve dot products, purely because the representation was chosen well.

Which is best? The question is malformed. It depends entirely on what you are doing:

  • Live chat, user waiting — A. Nothing above 3 seconds is acceptable.
  • Overnight batch of 100,000 — B. D would cost $14,000 for four points.
  • Medical or legal triage — C. Accuracy dominates; reliability matters more than the extra points.

Look hard at D. It has the highest accuracy and is a bad choice in essentially every scenario. If your improvement loop optimises accuracy alone, it will happily walk toward D and report success.

19.2 · Pareto thinking

Pareto frontier

Plain meaning: the set of options where you cannot improve one thing without making another worse.

Technical definition: the set of non-dominated solutions — those for which no other solution is at least as good on every objective and strictly better on one.

Why it matters here: it splits your candidates into "genuinely a trade-off" and "just worse." The second group can be discarded without any judgement call at all.

19.3 · Making your system cost-aware

def objective(metrics, weights, constraints):
    """Score a candidate under explicit weights and hard limits."""
    if metrics["p95_seconds"] > constraints["max_latency"]:
        return float("-inf")                 # hard constraint: disqualified
    if metrics["mean_cost_usd"] > constraints["max_cost"]:
        return float("-inf")
    if metrics["reliability"] < constraints["min_reliability"]:
        return float("-inf")

    return (weights["accuracy"]    * metrics["accuracy"]
          + weights["reliability"] * metrics["reliability"]
          - weights["cost"]        * normalize(metrics["mean_cost_usd"])
          - weights["speed"]       * normalize(metrics["median_seconds"]))

Two mechanisms, deliberately different. Hard constraints disqualify outright — a 40-second agent in a 5-second product is not a trade-off, it is a non-starter. Weights handle the genuine trades among survivors. Conflating the two produces a scoring function that will happily accept an unusable agent because it scored well elsewhere.

Feed the diagnosis engine your cost budget too, and it starts proposing differently: with room to spend it may suggest reflection; near the ceiling it will look for a prompt fix instead. That is cost-aware optimization, and it is a genuinely differentiating feature to demo.

Mental model to remember

An improvement loop optimising accuracy alone will find the most expensive possible agent and call it progress.

20.2 · Why one run proves nothing

Non-determinism (§1.6) means every measurement is a sample from a distribution.

Reasonably settled. That interleaving reasoning with tool use helps on multi-step tasks (the ReAct line of work, Yao et al., 2022). Part XXV

Capstone

A task you have never seen. Work it yourself before reading on.

The challenge

All you are given

GOAL — "Given a research paper's abstract and a list of 200 candidate papers, identify which candidates the paper most likely cites."

TOOLS — fetch_abstract(paper_id), embed_text(text), search_similar(vector, k), extract_keywords(text), get_citation_count(paper_id)

EVALUATOR — 100 papers with true citation lists; scored by Recall@20 and MAP.

Design the system that generates, runs, diagnoses, and improves an agent for this. Stop reading and try it.

Hint one

Do not think about citations. Run the §16.2 parser: is needs_external_facts true? Is steps_known_in_advance true? Are inputs compound? Is the output checkable? Answer those four and the architecture falls out mechanically.

Hint two

Recall@20 over 200 candidates means a ranking problem, not a classification problem — which is structurally the same shape as §18's music domain, not §23.1's routing. What did the generator choose there, and why?

Hint three

Imagine round 0 uses embeddings alone and reaches Recall@20 = 0.42. Failures cluster on papers whose abstracts share no vocabulary with the query but are in the same subfield. Which taxonomy class is that, and which lever does §12.1 map it to?

The worked solution

   PARSER
     needs_external_facts   = true    (must read abstracts)
     steps_known_in_advance = true    (embed → search → rerank)
     inputs_are_compound    = false
     output_is_checkable    = true    (metrics computable)
     latency_sensitive      = false
   → select_orchestration() → "planner_executor"

   ═══ ROUND 0 ═══  R@20 0.42 · MAP 0.28 · $0.006 · 2.1s
     plan: [embed query abstract, search_similar(k=20), return]
     clusters
       ▇▇▇▇▇▇▇▇▇ 31/58  vocabulary-mismatch — same subfield,
                        different terminology
       ▇▇▇▇       9/58  highly-cited papers missed entirely
     diagnosis  tool_selection — extract_keywords and
                get_citation_count exist and are never called;
                embeddings alone miss terminology-divergent work
     lever      ORCHESTRATION (widen, then rerank on more signals)

   ═══ ROUND 1 ═══  R@20 0.61 (+0.19) · MAP 0.44 · $0.011 · 4.7s
     plan: [embed, search_similar(k=60),
            extract_keywords on query + candidates,
            rerank by embedding + keyword overlap,
            return top 20]
     clusters
       ▇▇▇▇▇▇    18/39  foundational papers ranked too low
     diagnosis  tool_availability→selection — citation count is a
                strong prior for foundational work; never used
     lever      ORCHESTRATION (add the signal to the rerank)

   ═══ ROUND 2 ═══  R@20 0.71 (+0.10) · MAP 0.53 · $0.013 · 5.2s

   ═══ ROUND 3 ═══  no dominant cluster → STOP

Now notice what you just did. You solved a domain you had never seen — using the same four questions, the same taxonomy, the same lever map as email routing and cover-song retrieval. Nothing about citation networks was required. That transferability is what the track means by "tasks it has never seen before," and it is now a thing you can do rather than a phrase in a brief.

The mental model that holds it all

Parse the task into properties. Generate from properties. Run and record everything. Cluster the failures. Diagnose to a root cause. Pull exactly one lever. Measure. Repeat until no mode dominates.
